# Functionize Prompting Skill

This skill teaches how to write Functionize **create-agent prompts** — the natural-language instructions that produce test steps in the Functionize Agentic Studio platform. The principles below apply whether the user is creating a new test, fixing a broken one, or asking for drafted instructions to paste into Functionize.

## Scope — what this skill covers

This skill covers requests like:
- "Write me a Functionize test for [workflow]"
- "Draft prompts to test [our checkout / signup / login flow]"
- "Fix this Functionize test instruction — it picked the wrong button"
- "Help me phrase a TDM-driven login test"
- "What's the right way to verify [X] in Functionize?"
- "Turn this existing Selenium/Playwright-style test into Functionize instructions"

If the user asks about Functionize **operations** (running tests, orchestrations, diagnostics, the agent session, the CLI), they need a different skill or to talk to the Functionize agent directly — this skill is purely about **writing the natural-language test instructions**.

**If a Functionize domain or app-context skill for the target application is available, load it** via the Skill tool — a domain skill by its `functionize-<app>` name (e.g. **functionize-salesforce**), an app-context skill by its name. It is the source of the app's facts a prompt needs: an app-context skill carries those facts **only**, a domain skill carries them **and** restates the craft in the app's terms. This skill stays the canonical source of the domain-agnostic craft — either way, *Decompose any flow* (below) takes the companion's facts into the prompt.

## The single most important rule

**Write intent, not mechanics — all the way down.** State the user-visible goal — "log in," "add to cart," "verify the order confirmation shows the right total" — in plain English. Never write CSS selectors, XPath, or click coordinates; and just as firmly, **never write platform syntax** — no value tokens, no verification operators, no action-type names. You describe *what you want in words*; the Functionize platform generates the steps and materializes any token, operator, or selector.

| Don't write | Do write |
|---|---|
| `Click button with selector #submit-btn` | `Click the Submit button` |
| `Type "alice@test.com" into input[name="email"]` | `Enter the email from the login variable` |
| `Wait 2 seconds, then click .product-card:nth-child(1)` | `After the search results load, click the first product` |
| `Type "United States" into the country field` | `Select "United States" from the Country dropdown` (native select; typeaheads: type the **full** value "United States", then select the single exact match; never a fragment-then-pick unless the user specifies — `fundamentals.md` "Searching for a record") |
| a generator token in the field | `Generate a random email on the functionizeapp.com domain` |
| `Verify h1.title.text == "Welcome"` | `Verify the welcome heading is displayed` |

## Every prompt verifies a real outcome — that is this skill's job

Write every prompt so the test asserts the real outcome it set out to prove — a durable result, never a transient toast. That is woven through the rules here — a terminal outcome verify (#26), a runtime value captured into a variable and referenced by name (#17/#27/#28), durable state over transient events, a structural check for volatile content (#16). Written right, the outcome is real *by construction*, so a green run means the thing you set out to prove actually happened.

## Prefer the platform's native capability — fall back to manual only when needed

The companion to "write intent, not mechanics": for any task, **prefer the Functionize-native mechanism and supply the context it needs** — reach for a hand-written custom-code / manual workaround only when no native path covers the case. The fallback is legitimate when it's genuinely needed; it is a *fallback*, not the default.

| Task | Native first (preferred) | Manual fallback — only when needed |
|---|---|---|
| Dates / times | a **date picker**, or a **relative-date intent** ("a delivery date 30 days from today") — `references/fundamentals.md` #13 | a computed-date custom-code step **only** when you need the exact value to *verify* later, or for a typed (non-calendar) field |
| Random / unique data | a **generated value** — describe it in English ("a random 8-character string") — `references/native-actions.md` | a custom-code generator only for cases no built-in covers (e.g. a checksum-valid VIN or IBAN, or a value derived from other fields) |
| Outbound HTTP | the platform's **native API call** ("call `POST /orders` with …") — `references/specialty-steps.md` §1 | (never a custom-code `fetch()` — CSP/CORS-blocked) |
| File checks | native **download checks** | an Extension **only** to read *inside* a file — `references/specialty-steps.md` §3 |
| Email / 2FA | the native **email reader** (`functionizeapp.com` inbox) | custom polling only if the native reader can't reach the inbox |
| Capturing an element value | a **native verify-capture** — *verify [the element] and capture it as [name]* — `references/fundamentals.md` §4 (a) | custom JavaScript **only** when no element verify can reach the value — `references/fundamentals.md` §4 (a) |

**"Include the context for that to be done" is the other half** — a native capability still needs the right inputs: a relative date stated as intent, a real file source named for an upload (#23), a project variable resolved before it's referenced (#21). Supply that context and let the native path do the work; only when it genuinely can't express the case do you drop to a manual step.

**Phrase an entry *method* as a preference with an explicit fallback — for method choices that have a genuine working alternative.** Dates are the canonical case (a **date picker vs. a typed date**, #13); file uploads are another (a standard vs. a **JavaScript-mediated** upload — `references/specialty-steps.md` §3). For these, naming the method is sometimes the reliable default, but pinning it hard removes the latitude to recover if it isn't available — so **phrase it as a soft preference with an explicit fallback** rather than locking it in (full date-field rule and wording: #13). Pin it hard **only when the user specifically requires it** ("it must use the date picker") — then state it as a firm constraint and omit the fallback. **This does *not* override the firm rules for native dropdowns and typeaheads:** a native `<select>` takes a *chosen option, never typed text*, and a typeahead follows a deterministic observable-state rule — a soft "fall back to text entry" there is exactly the mis-type that does nothing. Those controls follow `references/fundamentals.md` §1 "Selecting from lists," not this default.

The platform's native capability is wide, and almost all of it is generatable from natural-language intent. **The platform picks the mechanism from the *verb* you use** — choose the right verb and name the target in words, never the mechanism or its syntax; **generated values** work the same way (*"generate a random email on the functionizeapp.com domain"* — describe it in English, never a token; prefer a generated value over a hardcoded literal, dates especially, #13). Before hand-rolling a custom-code step, check whether a native path already covers it: the full native surface, the generated-value phrasebook, and the two editor-only exceptions are catalogued in `references/native-actions.md`.

## Show-and-confirm — the prompt and the test are two steps, with the user between

**This is automatic, not a suggestion.** Writing the create-agent prompt and generating the test are **two steps, with the user's approval between them.** Before any prompt — new *or* corrected — goes to the create agent, show the prompt once and wait for the user's answer. Creating a test spends real budget and produces a real record — treat it like any irreversible send: never fold writing and generating into one unbroken pass, however the request is phrased (*"make a test to…"*, *"build me a test…"* is authoring first and generation second, never a license to generate straight through).

❌ Wrote the prompt and generated the test in one pass — the user never saw it.
✅ Wrote the prompt, showed it, waited for the go-ahead, then generated.

Two explicit user acts waive the *show* — never the rule itself, and never the readiness check: *"use mine"* honors the user's wording; *"create it without showing me"* skips the review, and you generate your best rewrite unshown. A user who only wants prompt text to paste elsewhere never reaches this step — don't manufacture an approval. A waiver drops the *show* only: an unresolved readiness STOP (#5/#21) and the hard refuses (#4/#6/#25) still fire first, and a suite split-confirm (*Suite requests*, below) still shows — it decides scope, not wording.

The mechanics — showing the assembled prompt, waiting for the answer, re-showing after a tweak — live with the full procedure in *Workflow when writing a prompt from scratch*, step 8.

## Credentials & secrets — always variabilize, never plaintext

**This is automatic, not a suggestion.** Any time the user hands you a real credential or secret — a username, password, API token, a **designated test card** number, OTP seed, connection string, anything sensitive — you must move it into a **named masked variable** and reference *only the variable's name in words*. Never echo the literal value back into the test instructions, an `<!-- comment -->`, the test name, or your own chat reply.

Procedure, every time:
1. **Detect** the sensitive value in the user's request.
2. **Name a variable** for it (e.g. `test_user_password`, `api_token`, `checkout_card`). Reuse an existing one if the project already has it.
3. **Write the prompt referencing the variable by name** — *"the password from the masked preset variable named `test_user_password`"* — never the value, never a token.
4. **Hand the user a "set these in the platform" list** of variable names → mask the actual values as `••••` in anything you write. The user sets each secret as a **masked execution-preset variable** (Project → Execution Presets), where it is encrypted in the keystore and hidden in logs, screenshots, and artifacts; a **secret project variable** (Project → Variables, marked secret) is fully supported and is the home where presets aren't available.

```
User: "Write a login test. The account is qa@acme.com / Hunter2!Pass"
❌ Enter qa@acme.com and Hunter2!Pass into the login form
✅ Enter the email and password from the preset variables named test_user_email and test_user_password (test_user_password marked masked) into the login form
   → Set in Functionize (Project → Execution Presets): test_user_email, test_user_password (masked)
```

**Payment cards:** what you variabilize is a *designated* test card — one a real gateway accepts (the `checkout_card` pattern above), never a real card. There is **no synthetic-card generator**; even a field that only needs a valid-format card takes a designated test card from a masked variable, not an inline value. Full phrasing lives in `references/native-actions.md`.

Exceptions that may stay inline: throwaway values the test *generates itself* (e.g. a brand-new signup password) — but even those are cleaner as a named variable so the value isn't baked into the prompt text. Bulk test logins belong in a TDM datasource (a credentials column), not inline.

**Which home:** a human-set secret → a **masked preset variable**, or a **secret project variable** where presets aren't available; human-set per-environment config → a **non-masked preset variable**; a value one test writes for a later test → a **project variable** (presets are read-only). Full decision table: the `functionize` skill → `references/dsl-and-actions.md` ("A variable's home").

## Capturing a runtime value — capture it into a variable, reference the variable

A value the test **produces or reads back at runtime** — an order id or confirmation number on a results page, a total, a received OTP / verification code, an id from an API response, a tracking number returned by an async submit, anything the agent reads at generation time that will differ on the next run — follows one discipline: **capture it once into a named variable, then reference that variable** wherever it is reused. Canonical shape: *verify [the source] holds a value of the right shape and capture (or extract) it, setting it as a local variable named [name]*, then *enter (or verify against) the [name] variable*. The verb **capture/extract** forces a read at runtime; **set it as a local variable** stores it; referencing **the stored variable** downstream keeps every use pointed at the one captured value — never re-read the value at each use, never restate it as a literal. Two shapes silently break this: a **bare, unnamed capture** (*capture the name used*) leaves nothing for a later line to reference, and a **prose reference** to the value (*"the captured Opportunity name"* rather than `oppName`) leaves no handle to bind — so the variable gets re-inferred or dropped.

**A value worth capturing is a value worth verifying.** For a value read from a discrete **element** — a page field, or a targetable email-reader value — the default is one shape, every time, regardless of downstream use: *verify [the element] [loose check] and capture it as [name]* (anti-pattern #28). The verify names which element and how success is judged, and stores the value on the same line — so there is no per-capture "do I guard this?" decision. The old compared-vs-re-entered cut survives only as the *why* (a compared or write-only value passes silently when empty; a re-entered one fails loudly — but you verify-capture either way). Two carve-outs: a **native non-element source** (the URL, a downloaded filename) is a plain capture, nothing to verify; and **custom JavaScript** is the fallback only when no element verify can reach the value (embedded in free text, computed, or a no-DOM surface). The uniform rule, the plain-operator palette (no regex), and the boundary live in `references/fundamentals.md` §4 (a).

```
❌ Read the verification code from the email and enter it.  (bare read — no verify, and the snapshot trap #27)
✅ Element, re-entered later → still verify-capture: verify the verification-code (a discrete element in the email reader) is not empty and capture it as a local variable named otpCode, then enter the otpCode variable.
✅ Element, compared later → verify-capture: verify the order number is not empty and capture it as a local variable named orderId, then verify the confirmation page shows the orderId variable.
❌ Self-generated, reused later → Capture the Opportunity name used … verify the record shows the Name matching the captured Opportunity name.  (unnamed capture + prose reference — no handle to bind, #17)
✅ Self-generated, reused later → generate a unique Opportunity name and set it as a local variable named oppName, then verify the record page shows the Name matching the oppName variable.
```

This is the default for any reused runtime value (a secret instead follows *Credentials & secrets* above; a pre-existing project value, *Referring to a project fixture* below). It avoids the **snapshot trap** — phrasing a reuse as *"read the code and enter it"* can produce a one-time literal in place of a live read (anti-pattern #27); capturing into a named variable and referencing that variable keeps every use pointed at the value the run actually read. Full phrasing and the local / project / preset scopes live in `references/fundamentals.md` §4 (Capture and reuse patterns).

## Referring to a project fixture — "the configured X", never a token

A pre-existing **fixture** — an org-varying id, URL, or value a human sets in the project (resolve it before referencing, anti-pattern #21) — is referenced by *intent*: you name the value in plain English, never the platform's internal variable token. Name its **home** in the parenthetical — stable **per-environment config** (an instance/base URL, a region) is a *preset variable*; a value one test writes for a later test is a *project variable* (see *Credentials & secrets* → "Which home" and the `functionize` skill → `dsl-and-actions.md`). How you name it scales with density:

- **Sparse — a lone reference where the concept is clear → name it lightly inline.** A type annotation — *"the org's instance URL (a preset variable)"* — or the variable by name in prose — *"the base URL from the preset variable named `api_base_url`"* (the form the reference files use). No header needed. **The parenthetical is always the plain *"(a preset variable)"* / *"(a project variable)"*** — a variable's actual name goes in the prose form or the header, never crammed into the parenthetical as *"(the X-id project variable)"*.
- **Dense — 3+ fixtures in a single instruction line, or a fixture referenced multiple times across the scaffold → "the configured X" + an enumerating header.** The header is what gives *"the configured X"* its meaning: list every fixture once in an HTML-comment header — **if the scaffold has none, add one; never write "the configured X" without a header entry for it.** In the body refer to each by **concept** — *"the configured account"* — never re-naming its variable; the header names the variables, the body does not. That is why *"the account named by the account-id project variable"*, repeated across a sentence, is banned: it re-does the header's job and collapses under density. (**Secrets are the exception** — a credential is always named by its variable per *Credentials & secrets* above, *"the password from the masked preset variable named `test_user_password`"*, so the user knows which to set; never "the configured password".)

```
✅  <!--
      Required project variables:
        the account-id project variable
        the offset-account-id project variable
        the cost-center-id project variable
    -->
    …a 500.00 debit on the configured account and a 500.00 credit on the configured offset account,
    each carrying the configured cost-center worktag…
❌  …a debit on the account named by the account-id project variable and a credit on the account named by
    the offset-account-id project variable, each carrying the cost-center worktag named by the cost-center-id project variable…
```

**In an API/URL step the contract stays literal.** The endpoint path, method, query params (incl. OData `$filter`/`$select`), response-field names, and status codes are real API contract — write them **verbatim** (`POST /projects`, `data.id`, `SupplierInvoiceStatus`, `200` are contract, not tokens). Reference any fixture in them as "configured" (covered by the header); **describe only the request *body* in prose** — never splice a fixture/generated value into a JSON literal, never invent a `{…}` placeholder (a static test-data literal is fine). Do **not** prose-ify the path/filter/field names or push discovery (`$metadata`) onto the author. **If the exact endpoint or field isn't pinned yet, write a literal stub** — `GET /orchestrations/{id}/runs` (status field TBC) — with a "confirm in the live pass" note, so the reader sees discoverable contract, not a concept to describe.

```
✅  <!-- Required preset variables: the Studio API base URL, the API CSRF token (masked), the team-id -->
    Call the create-project endpoint (POST /projects) on the configured Studio API, sending the configured
    CSRF token in the X-CSRF-Token header. The JSON body carries a unique title and the configured team id.
    Verify the returned id (response data.id) is not empty and store it in a local variable.
❌  Call POST {the API base URL}/projects with body {"title": "Studio Seed " plus a random 8-char suffix, "team_id": the team-id project variable}

✅  GET /sap/opu/odata/sap/API_SUPPLIERINVOICE_PROCESS_SRV/A_SupplierInvoice?$filter=SupplierInvoice eq '<the captured invoice number>'&$select=SupplierInvoiceStatus,PaymentBlockingReason on the configured tenant (basic auth, the configured API user); verify one record — SupplierInvoiceStatus posted, PaymentBlockingReason empty.
❌  GET the supplier-invoice service filtered by the captured invoice number, reading $metadata first for the fields. (path/$filter/fields prose-ified + discovery offloaded onto the author)
```

**Values the scaffold *produces* are not fixtures — they stay inline**, referenced by what they are (a generated value described in English per *Prefer the platform's native capability* above; a captured id/name per anti-pattern #17) — never "configured".

## Every wait needs an anchor

A wait must name a concrete visible element or state, **never "the page."** *"Wait for the page to load / processing to finish / the run to finish"* names nothing concrete to synchronize on; name the exact control or state the next step depends on — *"wait until the order-confirmation header is visible."* This is the most common real-world prompt-quality miss. Full rule (visible-vs-enabled, async persistent-element anchors) in `references/fundamentals.md` "Waits and synchronization."

## Top anti-patterns to refuse

When the user asks for any of these, push back and offer the correct alternative. **Each entry is a condensed summary; the full write-up for items #9–#22, #25, #26, #31, #32 lives in `references/fundamentals.md` §5 (i) — items that live elsewhere name their file or section inline. #33–#39 are self-contained here.**

1. **Defensive verification bloat** <!-- ap:defensive-verification-bloat --> — verify after every click. Verify only at logical checkpoints (the outcome of a flow).
2. **Vague omnibus verifications** <!-- ap:vague-omnibus-verification --> — "verify everything on the page looks correct." Replace with specific field-level checks.
3. **Multi-flow tests** <!-- ap:multi-flow-test --> — one test that logs in as admin, creates a product, switches to guest user, buys it, switches back, deletes it. Split into separate tests. One test = one flow = one reason to fail.
4. **Hardcoded credentials/data** <!-- ap:credentials-in-variables --> — never. Auto-variabilize every secret into a **named masked variable** — a masked preset variable, a secret project variable where presets aren't available, or a TDM credentials column — per the *Credentials & secrets* rule above. This is non-negotiable, not a stylistic preference. **Non-secret data is the mirror case, and need-based:** a value *earns* a variable only when reused, environment-varying, format/locale-sensitive, or collision-prone — otherwise it stays inline; don't reflexively variabilize plain one-off config (`references/fundamentals.md` §5 (e)). This never softens the secret rule above.
5. **Under-specified start state** <!-- ap:under-specified-start-state --> — "Navigate to the dashboard and create a report." The agent doesn't know if the user is logged in. Add: "(user is already authenticated)" or include the login steps explicitly. **The inverse also bites:** for guest/browse/anonymous flows, **state that no auth is needed** — *"No login required — browse as a guest."* Without it, a login step you didn't ask for may be generated. **A related trap is the *starting URL*:** a created test begins at an entry URL that **defaults to the project/environment URL** when nothing else provides one — frequently the wrong entry point (an SSO/IdP or portal host, not the app). **When a component is the first step (typically a login component), it carries its own URL and that is the entry — use it unless a different starting URL is specifically specified; otherwise don't set, supply, or default a starting URL, and never use the env URL, regardless of environment count.** Only when no component leads the test do you resolve the entry URL (an application of #21): ask which environment if there are 2+, or ask for the username, password, and starting URL — credentials in named masked variables (a masked preset variable, or a secret project variable where presets aren't available), never invented. Full write-up in `references/fundamentals.md` §5 (f).
6. **CSS selectors or XPath in the prompt** <!-- ap:intent-not-mechanics --> — these defeat the whole platform. Use intent. (Force-selector exists as a platform-level feature for legacy recorded tests — that's separate from writing selectors into a create-agent prompt, which is always wrong.) **Naming a labeled control IS intent, not a mechanic** — `Click "Convert"`, `Click the "Save and New" button` name what the user sees and are correct; the rule forbids *positional or structural* targeting ("the third button", a selector, an element id), not a control's visible label. Don't over-correct a good named-label line into something vaguer.
7. **Wrong line-prefix formatting** <!-- ap:numbered-bullet-lists --> — three prefix shapes corrupt step generation. **Numbered bullets** conflict with the generated step indices. **A `-` on every instruction line** is worse: a `-` marks a *sub*-step grouped under the preceding line, so dashing every line leaves no top-level parent to attach to, and the lines generate as a single step. **The same trap hides under a lead-in that looks like a legitimate parent** — a checklist of *independent* assertions dashed beneath a `Verify … :` / `… shows:` line (*"Confirm the page loaded:"* then *"- the heading reads X"*, *"- the New button is visible"*): the dashed lines attach to that one lead-in and collapse into a single bundled step — the §2 one-check-per-verify trap. An agent reformatting prose into bullets injects exactly this. Top-level objectives are **plain lines**, and **each independent assertion is its own plain `Verify` line**; reserve `-` only for the sub-fields of a compound *input* line (fill a form → its fields), never a list of independent verifies. Full rule in `references/fundamentals.md` §1–§2.
8. **Blank lines as section markers** <!-- ap:blank-line-section-markers --> — the create agent ignores blank lines, so they carry no meaning as section markers; use HTML comments (`<!-- ... -->`) for author-side metadata. (Spacing an assembled prompt for readability is a separate, fine thing — `references/fundamentals.md` §1.)
9. **One giant long flow when it could be segmented** <!-- ap:segment-long-flows --> — segment long E2Es at clean boundaries and chain via an orchestration; a flow too long to generate atomically puts every downstream instruction behind its first weak link.
10. **Leaving business-critical master data unspecified** <!-- ap:pin-master-data --> — **pin known-good IDs as project variables** (or add a validate-and-retry) so the test uses a known-valid record rather than whichever row a search happens to surface.
11. **A verify that can't run against the real value on a dynamic-result page** <!-- ap:dynamic-result-page-false-pass --> — on a blank/POST result page, read the result without navigating away and add a fail-fast clause, so the verify runs against a real value rather than an empty or already-replaced page.
12. **Verifying a value captured earlier in the same run is the single most generation-expensive verification** <!-- ap:captured-value-verify-cost --> — limit to one dynamic-value cross-step check per test; verify stable parts normally.
13. **Expecting direct typing to fill date/time picker fields** <!-- ap:date-picker-preference --> — phrase the method as a *preference with fallback latitude*, not a mandate; state relative dates as intent.
14. **A blanket "dismiss the cookie banner if it appears" on a site that has no banner** <!-- ap:cookie-banner-when-absent --> — only add a banner-dismiss line for sites that actually show one, scoped tightly to the consent control.
15. **Driving on-site search when a stable deep-link exists — especially on bot-protected sites** <!-- ap:deep-link-over-search --> — navigate directly to the predictable URL instead of typing into site search.
16. **Verifying volatile, live content on a dynamic feed/listing** <!-- ap:volatile-content-structural --> — phrase the check structurally ("at least one result", "multiple ranked stories"), never the value that happens to be there today. **An empty-state message is the same trap inverted** — asserting one that only holds for the current data (*verify the list shows "No items found."*) breaks the moment someone adds a row; either own the data (create or clear the specific rows you assert — then it is #31's owned-absence pattern) or assert stable structure present regardless of data (the page heading, the primary create/add control).
17. **A runtime value referenced without capturing it into a variable** <!-- ap:capture-before-reuse --> — capture any produced/received value (a generated random, a captured id/total, a received OTP/verification code) once into a named variable and reference it by name. A bare-referenced random yields two different values; referencing the named variable keeps every use pointed at the one value the run read. A login artifact's entry URL follows the same discipline — keep it a live project-variable reference so it tracks across environments.
18. **Naming a page/section/component the prompt hasn't confirmed exists on the target** <!-- ap:name-only-confirmed-targets --> — name only verified sections and add a skip clause; without one the run keeps searching for a missing-but-named target.
19. **Hardcoding a *specific* item in a browse/listing flow instead of selecting relatively** <!-- ap:relative-selection-browse --> — for browse/category/search over static catalog, instruct relative selection ("the first product in the grid").
20. **Selecting or asserting a STATEFUL or SHARED record by position, recency, "any", or by matching arbitrary text instead of a value it owns — the isolation contract.** <!-- ap:data-isolation --> *Every test owns the data it touches:* SEED the record it mutates or verifies (capturing the id or a unique name) or PIN read-only data by a stable identifier — never "the first/most-recent/any" record, and never a **membership check that matches a pre-existing row by arbitrary text rather than a value it owns — one it created and captured, or a stable identifier it pinned** (that row may not exist, may be renamed, or may sit on a later page — it proves nothing); a bare "the list has rows" is instead a structural check (#16), and a static read-only browse selects relatively (#19). When you already hold the id and the app exposes a real direct route (#18), open the record directly rather than list-searching for it (#31). Teaching version in `references/fundamentals.md` §5 (h).
21. **Treating a PROJECT-SCOPED identifier as a known constant** <!-- ap:resolve-before-you-reference --> — *resolve, don't assume.* Component names, project-variable names *and values*, environments, datasources, and the target project are project-specific; verify each exists (a real value, not a placeholder) **and at the SCOPE the test references it** before referencing — a same-named variable at the wrong scope (project vs execution-preset) resolves *empty* and the run can pass without ever using the value. Else STOP and ask; never substitute, invent, loop, or auto-pick. This applies to org-varying **labels** too — roles, stages, statuses, queue names, record types — but only where a label is genuinely org-configurable **and** used as an identifier/target; a stable visible control label stays named directly (#6), and never assert a label against the same variable that supplies it (a tautology — and an empty-resolved variable passes hollow).
22. **Treating an async/agentic "generate" or "create" as synchronous** <!-- ap:async-generate-durable-artifact --> — don't chain the next step on a not-yet-produced artifact (wait for the produced row/link/file and capture its id), and verify the durable produced output (a new row, the rendered result with expected structure, the downloaded file) — not a transient spinner or "Completed" status. **And if the generation can fail** (a card that never resolves, a 404, an error overlay, a status that never completes), don't author downstream steps that assume success — the fail-fast is the durable-artifact verify failing, not a literal "stop" line (author-side, per #25).
23. **Writing a file-upload step without providing a real file** <!-- ap:upload-needs-real-file --> — a bare "upload a file" names no source, so there is nothing for the step to upload. Always name a confirmed real source (attached at create time, a datasource fixture — project-scoped, resolve it first #21 — or a file produced earlier in the run); if none is in hand, work the provisioning ladder rather than guessing, and never emit a placeholder upload. Full write-up in `references/specialty-steps.md` §3.
24. **Re-scripting login inline instead of reusing one authored login artifact** <!-- ap:author-login-once --> — *author login once; reuse it.* Author the login flow as a reusable component (validated first — its own terminal step is a `Verify` of the authenticated state, #26) and invoke it by its exact name — adding its ID when you have one to disambiguate — where a name could match more than one component, the ID pins the intended one; otherwise the name alone suffices, and a missing ID is never something to ask the user for (#21, and the *Reusing a component* style rule) — from every test; never re-type the credential/OTP flow inline. This applies the component split rule (see `functionize`): **parameterize for data; split only when the login flow itself differs** (standard vs MFA vs SSO, a different role landing, tenant, negative-auth, or session-state). So tests that differ only in **credentials** — including multiple test users kept separate so concurrent runs don't collide — share **one** component, each supplying its own credentials (a project variable or an execution preset), never a clone. Never leave superseded, probe, or duplicate login tests.
25. **Writing author/environment context — or an author conditional — as a prompt instruction line** <!-- ap:author-context-in-steps --> — the create agent turns **every line into a test step**, so config facts (`(this account is 2FA-bypassed)`, "SSO off in this env"), setup rationale, and **author conditionals addressed to you or the agent** ("if an OTP prompt appears, stop and tell me") materialize **verbatim** as customer-visible steps. **The subtlest form is an aside appended inline to an otherwise-valid action line** — *Run the login component (username + password, no 2FA)* — which reads as a harmless annotation but still generates as a stray-comment step. A body line states **only what the test does or verifies**; everything else goes in a stripped `<!-- comment -->` header or is omitted. **A runtime test-branch conditional is the opposite — a legitimate step:** "if you see the 'Session expired' dialog, click 'Log in again'" is something the test itself runs, so write it as a standalone conditional (`references/fundamentals.md` §3), never a comment. Distinct from #8 (which is about *marking* metadata); boundary with #5 (a genuine start-state directive that changes which steps get generated is intent to keep).
26. **A test whose terminal step is not a durable-outcome verify** <!-- ap:terminal-outcome-verify --> — every test's final meaningful step must be a `Verify` that asserts the durable result the test set out to produce (authenticated state, a created record's id/field, a confirmation total/status, or — for a structural site — rendered content). Never end on a bare action (click/navigate/type), a `Wait until` (it only synchronizes and never asserts, so it can't prove the outcome), or a transient check (toast/spinner) — and **never itself conditional** (a verify behind an `if` asserts nothing when the condition is absent; §3). The verb decides whether a step asserts — `Verify` records a hard assertion; `Wait until` only synchronizes — so a login test ends on a `Verify` of the authenticated state, which fails loudly if the app isn't authenticated. The verify content must be **outcome-specific**: content that exists only *after* the flow completed, never a generic element also present on error/redirect pages. Distinct from #1 (don't verify after *every* click → do verify once, at the end, at the outcome), #2 (not a vacuous omnibus → the specific durable result), #11 (not volatile/generic → durable and outcome-specific). Edge cases still satisfy it: negative-auth ends on a verify of the error state; and a non-asserting step may trail the outcome verify **only when it reconciles state that outlives the run VM** — a persistent-state reset (preferably a dedicated teardown), a #30 project-variable hand-off write, or a server-side session invalidation — never a bare client-side logout (the VM tear-down already clears the session), which appears only when logout is itself the behaviour under test (ending on a verify of the logged-out state).
27. **Phrasing a reused dynamic value as "read it and enter it" instead of capturing it — the snapshot trap** <!-- ap:extract-dont-snapshot --> — *"read the code from the email and enter it"* can produce a one-time literal in place of a live read. Phrase it as a **native verify-capture** (#28) — *verify the source is not empty and capture it as a local variable, then enter the stored variable* — so the runtime read and the downstream reference are both unambiguous. Companion to #17. See *Capturing a runtime value* above; full write-up in `references/fundamentals.md` §5 (i, #17) and `references/specialty-steps.md` §4.
28. **Bare-capturing an element value instead of a native verify-capture** <!-- ap:verify-shape-before-capture --> — *a value worth capturing is a value worth verifying.* For a value read from a discrete **element**, use one combined instruction — *verify [the element] [loose check] and capture it as [name]* — the same shape whether it's later compared, re-entered, or write-only; a bare *capture it as X* drops the verify and can invite gratuitous custom JavaScript where a native read would do. Carve-outs (plain capture): a self-generated value (#17) and a native non-element source (URL, filename); custom JavaScript is the fallback only where no element verify can reach the value. Shape, not the exact value — plain operators, never a regex. See *Capturing a runtime value* above; full write-up in `references/fundamentals.md` §4 (a).
29. **Writing a TDM datasource read or write-back as a prompt instruction** <!-- ap:tdm-binding-not-in-prompt --> — a datasource column binds to a step field in the platform UI *after* generation and has no prompt token, so the binding happens by **attaching the column in the platform**, not by a prompt line. Write the step in **plain intent** and attach the column in the platform; a write-back's runtime value is the verify-capture (#28), but the **write itself is the attachment, not a prompt step**. Full rule (with the custom-JavaScript carve-out) co-located with the attachment teaching in `references/tdm.md` §3.
30. **Setting or capturing a runtime value straight into a project variable** <!-- ap:project-write-two-step --> — a project variable is **pre-created and platform-managed**; a native capture/`set` creates only a **local** variable. Handing a runtime value to another test is **always two steps**: verify-capture it to a local variable first (#28), then a **custom-JavaScript step** writes that local into the existing project variable. Write-side companion to #21; the project variable must already exist. Full write-up in `references/fundamentals.md` §4 (b).
31. **Asserting a record's presence or absence by reading the list as it sits instead of narrowing to the row** <!-- ap:narrow-before-membership --> — the on-screen list is not the whole list (it paginates / lazy-loads), so a **presence** check false-*fails* when the row is on a later page and an **absence** check passes **hollow**. Assert membership only on a **stateful/shared** row the test owns (#20): verify it at its own detail page by its captured id where one exists (§5(h)); else narrow the list first (search box, else column filter) and assert on that **rendered row**, never the raw on-screen list; for absence (the **owned-absence pattern**), bound the wait for the row to clear and assert the positive empty-state. (Static read-only browse selects relatively instead — #19; a bare "the list has rows" is a structural check — #16.)
32. **Asserting a gate denies without first confirming the precondition that makes the denial meaningful** <!-- ap:negative-test-confirm-precondition --> — a permission/feature-gate test can pass for the **wrong reason**: if the intended persona's login didn't take, the app is logged-out, and the redirect / 404 / "not available" from *that* state is structurally identical to the intended gate — so the test proves nothing about the boundary. Before inverting the verify, positively assert the intended persona is actually authenticated (the signed-in home shell renders) so a login failure fails loudly there. **A second precondition applies whenever you assert something *absent*: the gated thing must actually exist for a privileged persona** — a field/attribute/record/feature you assert absent must be present (and, for a field, *populated*) on an admin or privileged fixture, or the absence passes **hollow** (a never-populated field is indistinguishable from a suppressed one). Pin that populated fixture read-only; never seed a fresh, blank record for an absence test. Then assert the denial itself per §2 (#26). Scope: authZ/feature gates where login is *meant* to succeed (a bad-login test is the outcome itself — §2/#26).
33. **Acting on a privileged or state-dependent step without first proving the enabling state** <!-- ap:prove-enabling-state --> — before a privileged action, or one that depends on a **specific state a prior step was meant to establish** (a status, an entitlement), **verify (a hard assertion, not just a wait)** that the enabling surface/state actually rendered — e.g. the admin's member table before inviting a user; the record in the required status before acting on it. What separates this from #1 bloat: **guard only where a silent authz/state failure would otherwise let a *later* step false-pass** (the member table proves you're on the admin surface, not bounced) — not merely because an element must render or enable. The positive-flow twin of #32 — but the signed-in home shell that suffices there does not suffice here.
34. **Verifying a produced artifact only in a downstream view, or only once** <!-- ap:verify-artifact-home-and-persist --> — verify the thing you produced **where it lives** — its own detail page by the captured id (#20/#31), else its own row in its own list — not only a downstream view that could show a stale or orphaned copy; then **reload (or re-query) and verify again** — a single appearance isn't persistence. For an async-persisted artifact **bound the re-read** (poll/anchor for the row, per #22), never an immediate raw read that false-fails on eventual consistency. This persistence re-verify is the dynamic-value cross-step check to spend #12's budget on. For a **deletion**, it is the post-reload absence check (#31), not a produced row. Scope: creation/mutation flows. (#26 picks *what* to verify; this covers *where*, and whether to re-verify.)
35. **Building a test's fixture through a heavier path than the test needs** <!-- ap:cheapest-reliable-fixture --> — create the data a test needs by the **cheapest path that still yields a fixture faithful in the *inputs* its assertion depends on**, not a heavier end-to-end flow, **unless that heavier flow is itself what the test proves** (e.g. don't build a delete test's fixture through a chat/agent flow that can fail for reasons unrelated to deletion). Faithful in the **preconditions the test reads**, never in the **outcome it asserts** — the asserted result must be produced by the app under test (#37), never seeded (seeding an overdue invoice's *flag* instead of its past due-date is a tautology). A test that reads UI-defaulted fields needs the create path that applies them (cf. #10, on invalid records from guessed data). Distinct from #3 (combining unrelated flows in one test).
36. **Grouping a set-covering check as "and the rest" instead of enumerating it** <!-- ap:enumerate-set-covering-checks --> — when a check covers a set **fixed at authoring time** (each navigation destination, each variant, each required-field validation message), enumerate the members explicitly; "for each remaining item" can leave the members it doesn't name uncovered. A **runtime/volatile** set (cart line-items, a role-varying menu, search results) gets a **structural** check (#16) instead — never an enumerated generation-time snapshot. Sampling a **large** fixed set is fine for a **presence/coverage** check, but a set where each member asserts a **distinct value** (a per-state tax rate) enumerates every member regardless of size. Content, not formatting (distinct from #7).
37. **Seeding away a step that is part of the outcome** <!-- ap:seed-precondition-not-outcome --> — two questions, in order: (1) is this step part of *what the test proves* (an outcome) or a *precondition*? (2) **Only** if a precondition, seed it by the cheapest reliable path (#35). Seeding away half the outcome ships a half-test. **If it's an outcome, keep it in the test — but *how* follows the *production* flow, not what a super-user could do:** when production has **one** actor perform both parts, compose them into one session; when production **separates the roles across two or more actors** (maker-checker, segregation-of-duties, a permission grant-vs-deny pair), that separation is itself part of the outcome even if a super-user could fake it — **segment into one test per actor and chain via an orchestration**, handing each upstream record id to the next test per #30 (the permission-grant routing note below adds the pairing-coverage ownership). Distinct from #3: a single composite identity is fine, but context-switching between users inside one test is the multi-flow trap #3 forbids. Complements #35 (that is the *path*; this is *outcome-vs-precondition*).
38. **Proving a rule or gate fired with only one variant** <!-- ap:two-variant-rule-conditional --> — a rule-conditional step (a validation rule, an assignment/escalation/routing rule) needs **two seeded variants**: condition true → the rule acts; condition false → it correctly does **not**. One passing case can't distinguish an enforced rule from one that never ran. Two variants is the minimum for a **binary** gate; a **multi-way** assignment/escalation/routing rule enumerates each branch (#36) — "the rule acts" can't tell which branch fired. When variants differ only in **data/condition** they are two rows of one data-driven test (not two hand-written sub-flows — #3); when they need **distinct actors** they are two orchestrated tests per #37 — not one. Complements #32 (invert the verify on the deny side) and #37 (outcome-vs-precondition).
39. **Building one mega-test for a request that enumerated several independent flows** <!-- ap:split-enumerated-suite --> — when the request *lists* two or more behaviours that could each stand as its own test (nav, search, checkout), split it into one test per flow **before** drafting — see *Suite requests* above. The proactive twin of #3 (the interwoven multi-flow test, caught at request time by its enumerated shape). Distinct from #9 (segments one *too-long* journey and chains it — still one flow), #37 (segments across actors and orchestrates), and #36 (a set-covering check stays enumerated inside one test).

**Permission-grant tests need a paired control (a routing note, not a single-test rule).** A permission-*grant* test needs a paired **deny** control so a pass proves the grant, not a universally-open action — a two-test / coverage concern, segmented and orchestrated per #37 (the `functionize` skill owns orchestration), not a single-prompt refuse.

## Suite requests — split into one test per flow, confirm, then decompose each

**Before the readiness check, once per request: is this one flow or a suite?** When the request **enumerates two or more distinct behaviours that could each stand as its own test** — "check the nav, the search, and the checkout"; a "site health" ask that *lists* the areas to cover — **split it into one test per flow** and confirm the split before drafting any prompt, then run the rest of the pipeline once per test. One test covering everything goes red when any one part breaks; separate tests tell the user *which* part failed. This is the proactive form of #3 — catch the enumerated-flows shape up front, rather than refusing an interwoven multi-flow test once it is written.

**Fires only on an actual enumeration.** A bare breadth phrase that lists nothing — "test the site", "test everything", "site health" on its own — names no behaviour: that is an empty *Flow* slot, so it falls through to the readiness check's ask-once (below), never to a split. The trigger is two or more **individually nameable** flows in the request, each able to stand as its own test — not the scale of the words. Set-covering *checks* that belong in one test (each nav link resolves, each required-field message) are enumerated **within** one test (#36), not split into many.

**A single journey is one flow — never split it.** Login → add to cart → checkout, each step depending on the last, is one behaviour with one reason to run; splitting it into independent tests breaks what it proves. A journey merely *too long to generate atomically* is **segmented and chained via an orchestration** — a different move (#9), not a split.

**Split-confirm — show the plan and wait.** Present the split as a list the user approves: each test's name and its scope, then one ask. Give the tests a shared name prefix so they read as one set. This is its own gate, separate from and upstream of *Show-and-confirm* (which still runs later, once per drafted prompt). The two *Show-and-confirm* waivers do **not** reach it — they waive review of a prompt's *wording*; the split is a *scope* decision, so always show it.

> I'd split this into 3 tests, so a break points at the exact part that failed instead of one big red X:
> - **Site Health – Homepage Nav** — nav links, category dropdown, and footer render and work
> - **Site Health – Search** — searching a known term returns matching results
> - **Site Health – Checkout** — guest add-to-cart through to the checkout page
>
> Sound right, or want it split differently?

On approval, hand each test to *Decompose any flow* (below) in turn. This splits the coverage the **user** asked for; `functionize-coverage` runs the opposite direction — it *suggests* tests the user didn't name, inferred from change signals against an existing suite — so this applies whether or not coverage is installed.

## Decompose any flow

Turn any flow — even one with no ready-made template — into a create-agent prompt by running these moves in order. This is the **procedure**; where a move applies a catalogued anti-pattern it cites it by number (the single source of truth for that rule). A domain or app skill that carries only its app's facts defers here for the *how*, then packages the result via *Workflow when writing a prompt from scratch* (below). **A suite request runs *Suite requests* (above) first — bring one flow here at a time.**

**Before move 1, take the app's facts from the loaded companion.** The domain or app-context skill for the target app (loaded per *Scope*, above) carries the app-specific facts this procedure consumes — its **durable success signal (and how a denial appears), timing and async boundaries, identifiers, real vocabulary, and constraints** feed straight into *acquire → prove the enabling state → cue async → verify durable state* (move 4), the org-varying labels (move 5), and the negative-gate and rule-variant checks (move 6). If no companion is loaded, elicit those same facts from the user (folded into the single readiness question below) — resolve, don't assume; never invent an app fact (#21).

**Readiness check — before move 1, confirm the request is generatable.** A companion
supplies the app's facts, never *your* per-request flow or outcome — so a thin request
("create a test for example.com") is under-specified in any runtime, companion or not.
Check three slots:
- **Entry** — is the start resolvable: a component that actually leads, or a user-given
  starting URL (#5)?
- **Flow under test** — did the user name an actual behaviour to test, or only an entry
  point? The craft steps you supply — the terminal outcome verify (#26), proving an
  enabling state (#33), the persistence re-verify (#34), anchored waits (see *Every wait
  needs an anchor*) — need not be user-stated; only the *behaviour under test* must be.
- **Outcome** — did the request give, or the named flow *determinately* imply, a result to
  assert? A flow implying a definite end-state (login → authenticated) fills it; one with no
  discernible assertion leaves it empty (§ *Every prompt verifies a real outcome* / #26).

The **target** the slots attach to is the **behaviour under test** (its Flow slot), not the
site or app. A slot is filled by what the user gave for the behaviour the latest message
names — including a flow or outcome imported by explicit reference to an earlier turn ("same
as before but for X", "do that on the other site": same behaviour, new host). A **new
behaviour** is a *switched* target — the check fires even on the same app ("also add a test
for the refund path" after a checkout test) — while **refining the same flow** inherits the
working test's slots, even when the user names that flow ("make the login test more thorough"
is a refinement, not a switch — though a new assertion refills Outcome). Any slot empty →
resolve it before move 1; all filled → proceed.

**When a slot is empty — ask once.** Ask a single batched question covering every empty slot at once (never per-slot); when no companion is loaded the app-fact
elicitation (above) folds into this same question, not a separate ask. Offer a concrete
default the user can accept — for *Flow* and *Outcome* only; *Entry* is asked,
never defaulted (#5).

**On a decline — or an up-front deferral ("take your best judgement", which often arrives
before any reply) — draft only within these limits.** **Name each assumption inline** (a
named intent assumption is not an invented app fact — #21). The one flow-and-outcome you may
draft is browse-and-render with a **structural** check on rendered content ("I'll verify a
product listing is visible — good, or a specific outcome?") — a full durable outcome
(#16/#26), not a lesser one — and only for a companion-less **structural site**: one whose
value *is* the content it renders, with no login and no stateful app behaviour. If you can't
tell without a companion, it isn't one: never classify-as-structural to justify a draft, and
never invent the behaviour under test or a specific success signal (app facts the companion
supplies, move 4) — an empty Flow or a semantic Outcome then means STOP and ask (#21).
*Entry* is never drafted: resolve it or STOP-and-ask (#5), whatever a deferral said.

1. **Name the business outcome** — what the test proves and what would hurt if it broke. Test the app's real behaviour and customizations, not the platform's built-ins.
2. **Anchor the actor — one test = one authenticated session** (#3). Decide *fixture-vs-outcome* for any second actor or precondition before seeding (#37).
3. **Sketch the record/object chain and the automation between the nodes** — the automation's durable result — not "a record was created" — is what you verify (#26/#34); a missing automation gate is the silent failure.
4. **Per node: acquire → prove the enabling state → cue async → verify durable state.**
   - **Acquire by handle** — reach a record by the unique value you own for it (captured at creation, or a pinned stable id — its name or system id, #17/#20), never by position, recency, or a list row as it sits. The move is the same whether you *acquire* a record to act on or *locate one you just created to verify it*: open by held id via a confirmed direct route (not an assumed URL — #18), else search the handle and open the single result; where the surface has no search box, find its row by the handle, narrowing a paginated list first (#31). Search-vs-list is the create agent's call from what the page offers; the handle is the fixed part. Cheapest faithful fixture (#35).
   - **Prove the enabling state** before a privileged or state-dependent action — but only where a silent authz/state failure would otherwise let a *later* step false-pass, not before every action (#33).
   - **Cue async** only at real boundaries, each wait naming a concrete anchor (see *Every wait needs an anchor*); if the generate/create can fail, the durable-artifact verify is the fail-fast (#22).
   - **Verify durable state** in the artifact's home (#34) — reach that home by the record's handle (the acquire move above), not by scanning a list — never a toast (#26). The persistence re-verify is spent **once**, in the coverage-check (move 6) — not per node.
5. **Phrase each step as business intent** (#6); put org-varying labels in variables (#21).
6. **Coverage-check** — did you verify the automation's durable result, in one session? Enumerate any set-covering check explicitly (#36); a negative gate inverts the verify (#32); a rule-conditional step needs two seeded variants (#38); a **permission-grant or a genuinely multi-actor outcome** (production separates the roles — not a single super-user, who stays one session) segments + orchestrates (the routing note above / #37). Within #12's budget, **emit the persistence re-verify once** — reload/re-query the primary produced artifact and assert it again (#34) — not per node. **Flag any tempting-but-wrong assertion you deliberately dropped** for an *Intentionally NOT asserted* header note (step 7 / #25) — so a later editor or the create agent doesn't re-add it.

Then package via *Workflow when writing a prompt from scratch* (below): entry point / auth, variables, the `<!-- -->` header. **The prompt is now composed — stop and *show-and-confirm* (above) before anything is generated.** The acceptance gate is a *post-generation* phase you enter only after the user approves.

## Workflow when writing a prompt from scratch

Check *Suite requests* (above) first — an enumerated multi-flow request splits into one test per flow, and each flow then runs this workflow on its own. Run the (single) flow through *Decompose any flow* (above) first — that produces the ordered intent steps (they become step 4 here); the steps below wrap them with entry point, variables, header, the *show-and-confirm* step (step 8), and the acceptance gate (capture and verification come from the decomposition's moves).

1. **Goal** — named in *Decompose any flow* (move 1); confirm you and the user agree on what the test proves.
2. **Identify the entry point** — the entry the readiness check already resolved (#5). **Any login or authentication routes through `references/authenticating-test-users.md` (the one entry point)**, which states the precondition that the login can actually complete — a reader-readable (`@functionizeapp.com`) mailbox or a **2FA-bypassed** account. Never promise a login whose code the reader can't retrieve — confirm the account can actually complete the login, and confirm the run really signed in before relying on it (a run can report green on the steps it has even if the login step never received its code).
3. **List the variables needed** — credentials, payment data, search terms — and whether each is preset-scoped (human-set config/secrets), project-scoped (inter-test data pipes / secrets where presets aren't available), local-to-this-test, or TDM-driven (see *Credentials & secrets* → "Which home"). Any real secret the user gave you goes here as a **named masked variable**, masked in your output (see *Credentials & secrets*) — never inline in the prompt.
4. **Lay out the step body** — the intent-only lines from *Decompose any flow* (move 5), one logical objective per *plain* line (no leading `-`); reserve `-` sub-bullets for the fields of a compound line (multi-field forms), never as the marker on every instruction.
5. **Capture points** — from the decomposition's acquire/verify moves (above); confirm each value later steps reference is captured.
6. **Verifications at outcome points** — from the decomposition's verify-durable-state / coverage-check (above); once per outcome, not after every click (#1).
7. **Add an `<!-- HTML comment -->` header** documenting the variables required, expected duration, and any forward-dependencies — and, **when the flow has a non-obvious, tempting-but-wrong assertion you deliberately dropped**, an *Intentionally NOT asserted* note listing each dropped assertion and why (#25), so a later editor or the create agent doesn't "helpfully" re-add it. Omit it when there is no such exclusion.
8. **Show-and-confirm — the authoring workflow stops here** (this is the *show-and-confirm* seam, above; here is the procedure). Show the user the assembled create-agent prompt once and ask: *ready to create, or want to tweak?* Then wait: nothing goes to the create agent until the user answers. An already-strong prompt still gets shown; if the user offers adjustments, apply them and re-show, converging quickly rather than manufacturing extra rounds or friction. The two waivers (*"use mine"*, *"create it without showing me"*) and what a waiver never skips are stated in *Show-and-confirm* above; a hard refuse (#4/#6/#25) applies first regardless, and a craft rule like #26 you *flag* but honor if the user insists (they are in charge), then honor the user's wording and choices. **Show the prompt in a fenced code block, always** — the whole create-agent prompt, or (when fixing) just the changed lines as a block; never as inline prose. A variable name you mention in your own sentence is not prompt content and stays plain. Keep what you show a **clean create-agent prompt** — the intent lines plus the `<!-- -->` header, with no coaching or meta-hints for the agent baked into the body lines (its input is the prompt itself).

9. **A created test is done when it clears the acceptance gate.** A "generated" report is a starting point; a done test has generated fully and run green — clear the acceptance gate (the `functionize` skill → `verifying-a-created-test.md`). Your prompt-craft job is that the test's own final meaningful step asserts a real, durable outcome (not a transient toast) — including, for a login test, verifying the authenticated state — so a green run means the outcome really happened.

A complete annotated template lives in `references/fundamentals.md` (anatomy section). Ready-to-paste templates for the most common test types live in `references/templates.md`.

## Workflow when fixing a broken prompt

1. **Hand the failing run to the Functionize agent.** It diagnoses what failed, and you and the agent decide the repair — regenerate, a surgical step/field edit, or delete-and-recreate. Diagnosing the run and choosing the repair are not the prompt author's to infer from the artifact (`references/fundamentals.md` §6; `functionize` → `references/diagnostics-and-maintenance.md`). The steps below are your job only once the repair is a **corrective instruction**.
2. **Only change the broken line(s)** — don't rewrite the whole prompt. The terminal-verify obligation (#26) binds only the ending you **author or move**: a targeted mid-flow edit needn't retrofit a terminal verify onto an ending it doesn't touch, but an edit that **appends a new last step — or removes the existing terminal verify** — lands you back on #26 for the test's new ending. When the existing test has **no** terminal outcome verify and your edit doesn't touch its tail, honor the edit scope and **flag it, offering to add one** — a craft rule you *flag but honor* (from-scratch step 8), never a forced rewrite.
3. **Add disambiguation clues** — "the Submit button in the shipping section, not the Submit button in the payment section."
4. **Add capture clauses on earlier lines** if later lines reference values that weren't being stored.
5. **Show-and-confirm the corrective prompt** (from-scratch step 8) — show the changed line(s) as a fenced code block in context once, then get approval or an explicit override before it goes to creation.
6. **Re-clear the acceptance gate.** A fix isn't done until the regenerated/edited test clears the acceptance gate again (from-scratch step 9) — a green execution in which **any ending you authored or moved** asserts the real outcome (#26); a pre-existing terminal you didn't touch is out of this fix's scope (step 2). A "regenerated"/"PASSED" report alone is not a real finish.

## Style rules when writing prompts for the user

A pre-flight recap; each rule's full statement lives where it's taught:
- **Show the assembled prompt once and get the user's go-ahead before it goes to the create agent** — *Show-and-confirm* above / from-scratch step 8.
- **Plain top-level lines; `-` only for the sub-fields of a compound line; never numbered** — #7 / `references/fundamentals.md` §1.
- **In an assembled prompt you show the user, separate logical objectives with a blank line so it reads cleanly — blanks are readability-only, never structure** — #8 / `references/fundamentals.md` §1.
- **Name variables in plain English, never token syntax; never leave a secret inline** — *The single most important rule* above / *Credentials & secrets* (#4).
- **Capture a reused runtime value into a named variable, then reference the variable** — verify-capture element reads (#28), never *"read it and enter it"* (#27) — *Capturing a runtime value* above.
- **Author-side notes, setup rationale, and environment/account context go in `<!-- comments -->`, never as body lines** — #25 / #8.
- **Place each verify at an outcome moment on durable state, never a timed/transient event** — #26 / #1.
- **Every wait needs an anchor** — see *Every wait needs an anchor* above.
- **After generation, read the generation status and clear the acceptance gate** — from-scratch step 9.
- **Email loops (verification, 2FA) use `functionizeapp.com` addresses** — the built-in reader only handles that domain (`references/specialty-steps.md` §4).
- **Reuse a component by its exact full name; add its ID when you have one as a disambiguator — not required, and never ask the user for one you weren't given** — full rule #24 (record-opening component takes the id as input, #20; login component keeps a live entry-URL reference, #17).
